Variáveis de ambiente são pares de nome e valor que o seu projeto lê quando inicia, como o `TOKEN` do bot ou a URL de um banco. Elas valem em **todos os planos**, inclusive no Free.

<CodeGroup>
```js Node.js
const token = process.env.TOKEN;
```

```python Python
import os

token = os.environ["TOKEN"]
```
</CodeGroup>

## Pelo painel

Abra o projeto e vá em **Configurações** › **Variáveis de ambiente**.

- **Adicionar:** escreva o nome e o valor e salve.
- **Importar .env:** escolha o arquivo `.env` (**Escolher arquivo**) ou cole o conteúdo dele. Ele é lido no navegador, e só as variáveis entram na lista. Linhas com `#` são comentários e ficam de fora. Escolha entre **Mesclar** com as que já existem ou **Substituir todas**.

No **Novo projeto** também dá para adicionar as variáveis (ou importar o `.env`) antes de enviar: elas vão cifradas junto com o envio e chegam ao projeto antes de ele iniciar. Se o seu `.zip` traz um `.env.example` e não traz o `.env`, o painel já põe os nomes dele na lista, com os valores vazios para você preencher (veja [O modelo de variáveis não é lido](#o-modelo-de-variáveis-não-é-lido)).
- **Trocar um valor:** digite o novo valor na variável e salve. O valor antigo nunca aparece.

Depois de salvar, o painel avisa que o projeto recebe as variáveis **no próximo início** e oferece **Reiniciar agora**.

## O modelo de variáveis não é lido

O `.env.example` (e o `.env.sample`, o `.env.template` e o `example.env`) é só um **modelo**: mostra quais variáveis o código pede. A Cube não lê esse arquivo, e o seu projeto também não: quem lê o `.env` é o seu código, e só o `.env`. Quem edita o `.env.example` e envia o `.zip` assim sobe o projeto **sem nenhuma variável**: o código procura o `TOKEN`, não acha, sai com erro e cai a cada subida, até ficar em **Em loop de erro**.

Veja um modelo comum:

```ini .env.example
# Modelo: a Cube não lê este arquivo.
TOKEN=cole-seu-token-aqui
PREFIXO=!
```

Cada linha `NOME=valor` vira uma variável **no painel**, com o valor de verdade:

| Nome | Valor que você preenche |
| --- | --- |
| `TOKEN` | O token do seu bot, o de verdade |
| `PREFIXO` | `!` |

<Steps>
  <Step title="Envie o .zip no Novo projeto">
    Ao achar um `.env.example` e nenhum `.env` na raiz do `.zip`, o painel lista os nomes dele em **Variáveis de ambiente**, **vazios**, com a frase "Seu projeto pede estas variáveis. Preencha aqui: o arquivo .env.example é só um modelo e não é lido." Os valores de exemplo do arquivo **nunca são copiados**: só os nomes.
  </Step>
  <Step title="Preencha os valores">
    Escreva o valor de cada variável. Nomes que a Cube não aceita (veja as [regras](#regras)) ficam de fora, e a variável que você deixar **vazia não é enviada**.
  </Step>
  <Step title="Envie e inicie">
    O projeto sobe já com as variáveis. Num projeto que já existe, ao enviar um `.zip` novo com o `.env.example`, a confirmação **Confira antes de enviar** lista as variáveis que ainda faltam e salva o que você preencher antes de enviar.
  </Step>
</Steps>

Se o projeto já está em **Em loop de erro**, sem nenhuma variável e com o `.env.example` na pasta, o aviso no topo da aba **Projeto** diz isso e leva direto para **Configurações** › **Variáveis de ambiente** (nos planos pagos, que mostram os arquivos do projeto). Veja também [O bot caiu 5 vezes seguidas](/troubleshooting/discord-bots#o-bot-caiu-5-vezes-seguidas).

<Warning>
  Não ponha o token de verdade no `.env.example`: ele é um arquivo comum do projeto, vai no `.zip` e pode acabar no GitHub. Guarde o valor de verdade só nas variáveis de ambiente.
</Warning>

## Pela API

Use [Listar variáveis](/api-reference/projects/list-variables) e [Definir variáveis](/api-reference/projects/set-variables) com uma chave com as permissões `variables:read` e `variables:write`.

## Regras

| Regra | Limite |
| --- | --- |
| Quantidade | Até 50 variáveis por projeto |
| Nome | Letras, números e `_`, começando com letra ou `_`, até 64 caracteres (`TOKEN`, `DATABASE_URL`) |
| Valor | Até 4.096 caracteres, **numa linha só** |
| Total | Nomes e valores somados até 32 KB |
| Reservados | `HOME`, `PATH` e qualquer nome que comece com `CUBE_`. Em sites, `PORT` também |

<Tip>
  Precisa de um valor com várias linhas, como uma chave privada? Guarde em base64 e decodifique no código.
</Tip>

## O que já vem definido

| Variável | Valor | Pode trocar? |
| --- | --- | --- |
| `NODE_ENV` | `production` (Node.js) | Sim |
| `PYTHONUNBUFFERED` | `1` (Python: o `print` aparece nos logs na hora) | Sim |
| `PORT` | A porta do site (só em sites) | Não |
| `HOME` | `/tmp` | Não |

## Segurança

<Columns cols={2}>
  <Card title="Cifradas" icon="lock">
    Os valores ficam guardados cifrados. Depois de salvos, nunca voltam: nem no painel, nem na API, nem para Cube AI.
  </Card>
  <Card title="Fora da instalação" icon="package-x">
    As variáveis chegam só ao seu app, quando ele inicia. A instalação das dependências e o build não enxergam os valores, então um pacote malicioso não lê o seu token.
  </Card>
</Columns>

<Warning>
  Por não chegarem ao build, variáveis que o framework embute durante o build (como as `NEXT_PUBLIC_…` do Next.js) ficam vazias. Veja a dica em [Sites e APIs](/hosting/sites-and-apis).
</Warning>

A lista de [Atividade](https://app.cubehosting.com.br/activity) registra quem mudou as variáveis e quando, só com os **nomes**, nunca com os valores.
